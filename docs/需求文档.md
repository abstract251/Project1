## 1. 项目概述

### 1.1 项目背景

Web 服务器是 C++ 后端岗位的经典练手项目，能够完整覆盖操作系统（多线程/进程、I/O 多路复用）、计算机网络（Socket 编程、HTTP 协议）、数据结构（队列、缓存）等核心课程知识。本项目的差异化创新点在于 **配置热更新**：服务器运行期间修改配置文件即可生效，无需重启进程，这是实际生产系统中常见但学生项目中少见的特性，也是面试时的高价值话题点。

### 1.2 项目目标

- 实现一个可处理真实浏览器请求的轻量级 HTTP/1.1 静态文件服务器；
- 支持高并发连接，使用 epoll + 线程池的并发模型；
- 支持配置文件驱动启动，并支持运行时配置热更新（核心创新点）；
- 具备完善的日志系统，便于问题排查；
- 产出可量化的压力测试报告，作为简历加分项。

### 1.3 项目范围（明确做什么、不做什么）

**本阶段范围内：**

- HTTP/1.1 的 GET / POST 请求解析与响应；
- 静态资源（HTML/CSS/JS/图片等）服务；
- 并发连接管理（epoll 事件循环 + 线程池）；
- 配置文件解析 + 热更新；
- 多线程安全日志系统；
- 扩展功能：LRU 文件缓存、简易 CGI、压力测试报告。

**明确不做（非目标，避免范围膨胀）：**

- HTTPS / TLS 支持（本版本不考虑，如需要可作为后续方向）；
- HTTP/2、WebSocket、分块传输等高级协议特性；
- Windows / macOS 平台支持（epoll、inotify 为 Linux 专有，目标环境为 Linux 或 WSL2）；
- 动态路由、模板引擎、框架化路由分发；
- 反向代理、负载均衡。

### 1.4 术语定义

| 术语 | 说明 |
| --- | --- |
| epoll | Linux 下的 I/O 多路复用机制，用于单线程监听大量文件描述符的读写事件 |
| inotify | Linux 内核文件系统变化通知机制，用于监控配置文件修改 |
| 热更新 | 运行期间重新加载配置并生效，不重启进程、不中断服务 |
| 线程池 | 预先创建固定数量的工作线程，通过任务队列分发任务 |
| Reactor 模式 | 由事件循环（epoll）统一监听事件，再将事件分发给工作线程处理的并发模型 |
| 任务队列 | 线程池内部存放待处理任务的线程安全队列 |
| Keep-Alive | HTTP 长连接，同一 TCP 连接上处理多个请求 |
| LRU | Least Recently Used，最近最少使用缓存淘汰策略 |
| QPS | Queries Per Second，每秒处理的请求数 |

## 2. 运行环境与技术约束

| 类别 | 要求 |
| --- | --- |
| 操作系统 | Linux（内核 ≥ 4.5，推荐 Ubuntu 20.04+ / CentOS 7+）；开发可用 WSL2 |
| 编译器 | GCC ≥ 9 或 Clang ≥ 10（需完整支持 C++17） |
| 构建工具 | CMake ≥ 3.16，Make 或 Ninja |
| 依赖 | 仅标准库 + POSIX 系统调用（pthread、epoll、inotify、signal、fcntl 等），**禁止引入第三方库**（boost、libevent 等一律不用，突出自己实现） |
| C++ 标准 | C++17（使用 `std::thread`、`std::shared_ptr`、`std::atomic`、`std::string_view` 等） |
| 测试工具 | curl（功能验证）、webbench 或自写压测工具（性能验证） |

**技术选型说明：**

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| I/O 模型 | epoll（边缘触发 ET） | 高并发下优于多线程阻塞式 accept；面试考察点 |
| 线程模型 | 单 Reactor 主线程 + 固定大小线程池 | 事件监听与业务处理解耦，避免每个连接一个线程的资源浪费 |
| HTTP 解析 | **有限状态机**，不使用正则 | 正则逐行匹配性能差且易出错；状态机 O(n) 且可精确控制解析边界，是生产级服务器的标准做法 |
| 热更新实现 | inotify 文件监控 + 原子配置对象切换（shared_ptr / 双缓冲） | 无需重启进程；读线程始终拿到完整、一致的配置快照 |
| 日志写入 | 互斥锁保护的日志队列（可升级为异步日志） | 保证多线程写入不交错、不丢失 |
| 缓存策略 | LRU + 文件 mtime/size 校验 | 命中缓存前校验文件是否变更，保证内容一致性 |

## 3. 总体架构

### 3.1 模块划分

```
┌─────────────────────────────────────────────────────────┐
│                      LightWebServer                      │
├─────────────┬──────────────┬──────────────┬──────────────┤
│  Config     │  HttpParser  │  HttpHandler │  Logger      │
│  配置解析/热更新│  HTTP解析(FSM)│  请求分发/静态文件│  分级日志     │
├─────────────┴──────┬───────┴──────┬───────┴──────────────┤
│      EventLoop (epoll 主线程)      │      ThreadPool       │
│      连接管理 / 事件分发            │   任务队列 + N 工作线程  │
├───────────────────┬──────────────┴──────────────────────┤
│   StaticFile      │   LruCache (扩展)   │   CgiHandler (扩展)│
│   文件读取/安全校验 │   热点文件内存缓存    │   外部程序调用      │
└───────────────────┴─────────────────────────────────────┘
```

### 3.2 请求处理主流程（数据流）

1. 主线程 epoll 监听到新连接事件 → `accept()` 建立连接，注册到 epoll；
2. 监听到可读事件 → 读取 socket 数据到连接缓冲区 → 将"解析+处理"任务投递到线程池任务队列；
3. 工作线程取出任务 → HTTP 状态机解析请求行/头部/请求体 → 校验合法性 → 路由分发；
4. 静态资源：路径安全检查 → 查 LRU 缓存（扩展）→ 打开文件 → 构造响应报文（状态行 + 头部 + 正文）；
5. 响应写回 socket（可写事件驱动或直接写）→ 若 Keep-Alive 则复用连接等待下一请求，否则关闭；
6. 全程关键节点写入日志。

### 3.3 热更新数据流

1. 独立监控线程注册 inotify，监听配置文件所在目录（`IN_CLOSE_WRITE` / `IN_MODIFY` 事件）；
2. 配置文件被修改 → 监控线程触发重载 → 新配置写入临时配置对象（新 `shared_ptr` / 第二缓冲区）；
3. 对新配置做**完整校验**（见 5.3.3），校验通过后原子发布（`atomic_store` / 指针交换），并记录新版本号、加载时间、变更日志；
4. 校验失败 → 丢弃新配置、保留旧配置生效，记录 ERROR 日志（**失败回滚**，保证服务不中断、不进入坏状态）；
5. 所有请求处理线程在每次请求开始时获取当前配置快照（`atomic_load`），同一请求全程使用同一份快照，不存在读写竞争；
6. 额外支持 `SIGHUP` 信号触发重新加载，作为 inotify 不可用环境下的备用手段。

## 4. 功能需求

> 编号规则：FR = Functional Requirement。P0 = 必须完成（核心），P1 = 进阶（创新点），P2 = 扩展（加分项）。

### 4.1 FR-1 HTTP 请求解析（P0）

| 项目 | 需求 |
| --- | --- |
| 输入 | 连接缓冲区中的原始字节流 |
| 输出 | 解析结果：请求方法、URI、HTTP 版本、Header 键值对、Body、原始数据长度 |
| 解析方式 | 有限状态机，逐字节/逐行解析：`请求行 → 头部区 → 空行 → 请求体` |
| 支持的请求方法 | `GET`、`POST`（其余方法返回 `405 Method Not Allowed`） |
| Header 解析 | 不区分大小写键名（如 `Content-Length` / `content-length` 等价）；支持 `\r\n` 与容错 `\n` 行尾 |
| 请求体 | 依据 `Content-Length` 读取定长 Body；`Transfer-Encoding: chunked` 本版本不支持，遇到返回 `501 Not Implemented` |
| 边界条件 | ① 请求行/Header 总长度超限（如 > 8KB）→ 返回 `400` 并关闭连接；② Header 数量超限（如 > 100 个）→ 返回 `400`；③ 半包/粘包：数据不完整时等待更多数据，不提前报错；④ 空请求/畸形请求 → `400 Bad Request` |
| 性能要求 | 解析单个请求的时间复杂度 O(n)，不产生额外拷贝（直接基于缓冲区内存操作） |

**验收要点：** 用 curl / 自写用例覆盖上述全部边界条件，见第 8 章测试用例。

### 4.2 FR-2 静态资源响应（P0）

| 项目 | 需求 |
| --- | --- |
| 输入 | 解析后的 URI + 配置的根目录（document root） |
| 输出 | HTTP 响应报文（状态行 + 头部 + 文件内容） |
| 行为 | ① URI 与根目录拼接为真实文件路径；② 路径为目录时尝试追加 `/index.html`；③ 命中文件则返回 `200`，带 `Content-Type`、`Content-Length`、`Last-Modified`、`Connection` 等头部；④ 文件不存在 → `404`；⑤ 权限不足 → `403` |
| MIME 映射 | 至少支持：`.html/.htm`、`.css`、`.js`、`.json`、`.png`、`.jpg/.jpeg`、`.gif`、`.svg`、`.ico`、`.txt`、`.xml`、`.pdf`、`.mp4`、`.webp`；未知类型回退 `application/octet-stream` |
| 路径安全 | **必须拦截路径穿越**：规范化路径后（消除 `.`/`..` 及 `//`），校验最终路径必须位于根目录之内，否则 `403 Forbidden`（安全红线，见 6.3） |
| 支持 | 条件请求 `If-Modified-Since` → 返回 `304 Not Modified`（加分项）；HEAD 方法返回头部不返回正文（加分项） |
| 大文件 | 单文件大小不做硬限制，但超过阈值（如 1MB）时采用分块读写的流式方式，避免整文件载入内存 |

### 4.3 FR-3 并发处理：epoll 事件循环（P0）

| 项目 | 需求 |
| --- | --- |
| 监听 | 主线程 epoll 监听监听 socket 与所有客户端 socket |
| 触发模式 | 边缘触发（ET）+ 非阻塞 socket；数据需一次性读完（`EAGAIN` 处理） |
| 连接管理 | 连接对象（封装 fd、读缓冲、写缓冲、解析状态、Keep-Alive 状态、时间戳）挂载在 `epoll_event.data.ptr` 上 |
| 超时管理 | 空闲连接超时（默认 60s，可配置）自动关闭；使用最小堆或时间轮记录超时（面试加分点） |
| 可写事件 | 响应发送采用"先尝试直接写，写不完再注册 EPOLLOUT"的方式，避免大响应阻塞 |
| 最大连接数 | 受配置项 `max_conn` 控制，超出时对新连接直接拒绝并返回 503 |
| 优雅关闭 | 收到 SIGINT/SIGTERM 时停止接收新连接，等待在途请求处理完毕（带超时），再释放资源退出 |

### 4.4 FR-4 线程池（P0）

| 项目 | 需求 |
| --- | --- |
| 组成 | `std::thread` 固定数量工作线程（默认 = CPU 核数，可配置）+ 线程安全任务队列（`std::queue` + `mutex` + `condition_variable`） |
| 任务 | 以 `std::function<void()>` 封装"解析 + 处理 + 写响应"的完整任务 |
| 唤醒 | 任务入队后 `notify_one`；线程空闲时阻塞等待（`wait`），**不忙轮询** |
| 线程安全 | 入队/出队全程持锁；任务队列有容量上限（如 1024），满时对新任务做背压处理（丢弃或阻塞），防止内存无限增长 |
| 优雅关闭 | 线程池析构时设置停止标志 + `notify_all`，等待所有线程 join 完成 |
| 异常隔离 | 单个任务抛异常不允许杀死工作线程，需捕获并记录日志，线程继续服务 |

### 4.5 FR-5 日志系统（P0）

| 项目 | 需求 |
| --- | --- |
| 级别 | DEBUG / INFO / WARN / ERROR 四级，通过配置项 `log_level` 控制输出阈值 |
| 内容 | ① 访问日志：时间、客户端 IP、方法、URI、状态码、响应字节数、耗时；② 运行日志：启动/退出、配置加载/热更新、线程池状态；③ 错误日志：系统调用失败、解析失败、异常捕获（含 errno/strerror） |
| 线程安全 | 所有线程可并发调用，写入不交错、不丢失（互斥锁保护，或实现为异步日志：工作线程只入队，专用日志线程批量写盘） |
| 输出 | 默认同时输出到标准输出与日志文件；日志文件路径可配置 |
| 滚动 | 按大小滚动（如 10MB）或按天滚动，滚动时保留最近 N 个文件（如 5 个），防止磁盘占满 |
| 时间格式 | `2026-01-01 12:00:00.123 [INFO] message`，毫秒精度 |
| 性能 | 日志调用对请求处理主路径影响可控（异步日志时入队开销 ≤ 微秒级）；压测时 ERROR 级日志不成为瓶颈 |

### 4.6 FR-6 配置文件解析（P1）

| 项目 | 需求 |
| --- | --- |
| 文件 | 启动时通过命令行参数指定（`./server -c server.conf`），未指定时使用默认路径 `./server.conf`；文件不存在或解析失败 → 打印错误并退出（启动期配置错误不允许静默使用默认值） |
| 格式 | 每行一个键值对：`key = value`，`#` 开头为注释，空行忽略；值可带引号（可选）；key 大小写不敏感 |
| 配置项 | 见第 7 章配置项总表（含类型、默认值、校验规则） |
| 校验 | 解析后立即校验：端口范围、路径存在性、数值范围、枚举合法性，任一不合格视为解析失败 |

### 4.7 FR-7 配置热更新（P1，🔥核心创新点）

| 项目 | 需求 |
| --- | --- |
| 触发方式 | ① inotify 监控配置文件（`IN_CLOSE_WRITE` 为主事件，防半写状态）；② `SIGHUP` 信号手动触发（备用） |
| 生效范围 | 端口、根目录、日志级别、Keep-Alive 开关/超时、缓存大小、最大连接数等**全部配置项**均支持热更新 |
| 生效时机 | 文件保存（关闭写句柄）后 ≤ 1 秒内生效；不重启进程、不中断在途请求 |
| 原子性 | 所有读配置的线程要么看到完整的旧配置，要么看到完整的新配置，**不存在中间状态**（`std::shared_ptr<Config>` + `std::atomic` 发布，或双缓冲切换） |
| 一致性 | 单个请求从解析到响应全程使用同一份配置快照 |
| 失败回滚 | 新配置校验失败（非法端口、根目录不存在等）→ 丢弃并保持旧配置，记 ERROR 日志；服务器继续正常运行 |
| 变更记录 | 每次成功热更新记录：新旧配置 diff 摘要、生效时间、当前配置版本号；提供版本号供日志/接口查询 |
| 监控鲁棒性 | 配置文件被删除后重新创建（常见编辑器行为：先写临时文件再 rename）也能正确触发重载；监控线程异常退出需自动恢复 |
| 边界 | 热更新期间恰好有请求并发到达时不允许崩溃、死锁、数据竞争（可用 ThreadSanitizer 验证） |

**面试深度要点（文档提示，用于后续答辩）：** 为什么用共享指针快照而不是全局变量加锁？——读多写极少场景下，快照方案让读路径完全无锁，且天然保证一致性；全局变量方案要么加锁拖慢所有请求，要么出现读到一半的脏配置。

### 4.8 FR-8 简易 CGI 支持（P2，扩展）

| 项目 | 需求 |
| --- | --- |
| 触发 | 配置 `cgi_path` 前缀（如 `/cgi-bin/`）；URI 命中该前缀时不再走静态文件逻辑 |
| 执行 | fork + exec 外部程序（如 Python 脚本），通过环境变量/标准输入传递请求数据（QUERY_STRING、REQUEST_METHOD、CONTENT_LENGTH 等），从标准输出读取程序生成的 HTTP 响应 |
| 安全 | CGI 程序执行超时（如 5s）强制终止；CGI 输出不是合法 HTTP 响应时返回 500 |
| 限制 | 本版本仅支持 GET/POST，不支持 cookie 会话等复杂机制 |

### 4.9 FR-9 LRU 文件缓存（P2，扩展）

| 项目 | 需求 |
| --- | --- |
| 结构 | 哈希表 + 双向链表实现 O(1) 的 LRU；或 `std::unordered_map` + `std::list` 组合 |
| 命中策略 | 文件在缓存且 mtime + size 未变化 → 直接返回缓存内容；文件变更 → 淘汰并重读（保证强一致性） |
| 容量 | 按条目数 + 总内存字节数双上限控制（如最多 1024 个文件 / 64MB），超过时淘汰最久未使用项 |
| 并发 | 缓存访问加锁（读多写少可考虑读写锁）；文件内容只读共享，不拷贝 |
| 效果 | 静态资源压测下缓存命中时 QPS 显著高于磁盘读取（验收时对比数据） |

### 4.10 FR-10 压力测试与性能报告（P2，扩展）

| 项目 | 需求 |
| --- | --- |
| 工具 | webbench（`webbench -c 100 -t 30 http://127.0.0.1:8080/`）或自写压测工具（多线程 + epoll 客户端，统计 QPS、平均/99% 延迟） |
| 场景 | ① 小文件（如 1KB）静态页；② 中等文件（如 100KB）；③ 大文件（如 10MB）；④ 并发数 100/500/1000 梯度 |
| 指标 | QPS、平均响应时间、P99 延迟、连接成功率、内存占用（`top`/`/proc` 采样） |
| 报告 | 输出 markdown 报告：环境说明、测试方法、数据表、瓶颈分析与优化记录（如：先测无缓存 → 加缓存 → 再测，展示优化效果） |

## 5. 非功能需求

### 5.1 性能（NFR-1）

| 指标 | 目标值 | 说明 |
| --- | --- | --- |
| QPS（静态小文件，Keep-Alive，100 并发） | ≥ 5000 | 开启 LRU 缓存后作为对比项展示提升 |
| 并发连接数 | ≥ 1000 | 连接不泄漏、不超内存（每连接内存占用 < 10KB 量级） |
| 单请求处理时延 | P99 < 10ms（本机回环） | |
| 热更新生效延迟 | ≤ 1s | 文件保存后到新配置生效 |
| 热更新期间 | 0 请求丢失、0 崩溃 | 压测进行中反复改配置验证 |

### 5.2 可靠性（NFR-2）

- 任何异常路径（解析失败、文件缺失、系统调用失败、任务异常）都必须被捕获并记录日志，进程不允许崩溃（可用 `-fsanitize=address,undefined` 与 ThreadSanitizer 跑测试验证）；
- 优雅退出：SIGINT/SIGTERM 下在途请求处理完毕再退出（带最长等待时间）；
- 配置错误时具备失败回滚，服务可用性不受影响；
- 长时间运行（24h 压测）无内存持续增长（可用 `valgrind` / ASan 验证无泄漏）。

### 5.3 安全（NFR-3）

| 风险 | 防护措施 |
| --- | --- |
| 路径穿越（`../`、绝对路径、编码后 `%2e%2e`） | 路径规范化 + 根目录前缀强校验，违规返回 403（FR-2 安全红线，**必须**实现） |
| 慢速连接攻击 | 空闲超时机制（FR-3），超时强制断开 |
| 请求头轰炸 | 头部总长度/数量上限（FR-1） |
| 缓冲区溢出 | 所有缓冲区写入带边界检查；解析基于长度已知的内存块，不依赖 `\0` |
| 日志注入 | 日志内容中对 `\r\n` 转义 |
| 拒绝服务（超大 Body） | `Content-Length` 超上限（如 1MB）直接拒绝 |

### 5.4 可维护性与可读性（NFR-4）

- 模块化：每个模块一个目录（`config/`、`http/`、`net/`、`threadpool/`、`logger/`、`cache/`），头文件声明 + 源文件实现分离；
- 命名规范：类大驼峰、函数小驼峰、常量全大写下划线；关键模块必须有注释说明设计意图；
- 代码规模预估：核心功能 2500~4000 行（不含测试），符合"简历项目"体量，避免过度工程；
- 构建：`cmake .. && make` 一键构建；提供 `run.sh` / 测试脚本。

### 5.5 可移植性（NFR-5）

- 仅依赖 POSIX + Linux 专有接口（epoll/inotify），两者封装为独立模块并预留接口抽象，未来替换为 poll/kqueue 或轮询方案时只需改一个模块（这也是热更新备选方案 SIGHUP 存在的原因）。

## 6. 接口需求

### 6.1 命令行接口

```
Usage: lightserver [-c <config_file>] [-h]
  -c  指定配置文件路径（默认 ./server.conf）
  -h  打印帮助信息
```

### 6.2 配置文件格式（示例）

```ini
# LightWebServer 配置文件
port = 8080                # 监听端口（1-65535）
max_conn = 1024            # 最大并发连接数
thread_num = 4             # 工作线程数（>=1）
root = ./www               # 静态资源根目录（必须存在）
log_level = INFO           # DEBUG/INFO/WARN/ERROR
log_file = ./logs/server.log
keep_alive = on            # on/off
keep_alive_timeout = 60    # 空闲超时（秒）
request_max_size = 8192    # 请求头最大字节数
body_max_size = 1048576    # 请求体最大字节数
enable_cache = on          # LRU 缓存开关
cache_max_items = 1024     # 缓存最大条目数
cache_max_bytes = 67108864 # 缓存最大字节数
cgi_enabled = off          # CGI 开关
cgi_path = /cgi-bin/       # CGI 前缀
```

### 6.3 HTTP 行为约定

| 场景 | 状态码 |
| --- | --- |
| 正常响应 | 200 OK |
| 条件请求未修改 | 304 Not Modified（加分项） |
| 请求行/头部畸形、超限 | 400 Bad Request |
| 资源不存在 | 404 Not Found |
| 权限不足 / 路径穿越拦截 | 403 Forbidden |
| 方法不支持 | 405 Method Not Allowed（响应头带 `Allow: GET, POST`） |
| 请求头过大 | 413 Payload Too Large（或 400） |
| 内部错误（文件打开失败、CGI 失败） | 500 Internal Server Error |
| 超连接数上限 | 503 Service Unavailable |

响应头部至少包含：`Content-Type`、`Content-Length`、`Server: LightWebServer/1.0`、`Connection: keep-alive|close`、`Date`。

### 6.4 日志格式约定

```
访问日志：2026-01-01 12:00:00.123 [INFO] [ACCESS] 127.0.0.1 "GET /index.html HTTP/1.1" 200 5123 1.2ms
运行日志：2026-01-01 12:00:01.000 [INFO] [CONFIG] config reloaded to version 3 (port 8080 -> 9090)
错误日志：2026-01-01 12:00:02.000 [ERROR] [NET] accept() failed: Too many open files (errno=24)
```

## 10. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| epoll ET 模式下漏读/漏写事件 | 请求卡死、响应不完整 | 统一封装非阻塞读写工具函数，严格按 EAGAIN 语义处理；用例 TC-08 大并发覆盖 |
| 热更新与请求并发导致数据竞争 | 崩溃、脏配置 | 快照式配置对象 + atomic 发布；ThreadSanitizer 专项验证 |
| inotify 无法覆盖编辑器 rename 式保存 | 热更新不触发 | 监控目录而非文件 + 监听 IN_MOVED_TO；SIGHUP 备用 |
| 端口热更新失败 | 服务中断 | 先 bind 新端口成功再切换，失败回滚 |
| 压测 QPS 不达标 | 项目说服力下降 | 定位瓶颈（锁竞争/拷贝/日志），LRU 缓存与异步日志是主要优化手段，报告记录优化过程 |
| 范围膨胀（想做 HTTPS/HTTP2） | 工期失控 | 明确非目标（1.3），先保 M1/M2 质量 |
